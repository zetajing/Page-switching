# ADS 通讯代码检查

[返回文档导航](README.md)

检查日期：2026-11-13。范围包括配置与 Router 启动、手动客户端生命周期、监控读取、控制权心跳、批量读写错误处理、随附 ADS DLL 和退出清理。未连接真实 PLC，未修改自动造波控制或 PLC 程序。

## 本次已修复

| 问题 | 原来可能出现的现象 | 修复位置与行为 |
| --- | --- | --- |
| 手动首次连接只尝试一次 | 程序先启动、PLC 后上线时，监控能恢复，但手动一直未连接 | `AxisService.ConnectAtStartupAsync` 每次失败后等待 3 秒再尝试，首次成功退出；相同错误去重，关闭取消等待 |
| 持续连接失败未更新重试时间 | 第一轮等待 3 秒后，后续按界面刷新频率反复连接并记录日志 | `MachineMonitorService.RecordCommunicationFailure` 每次实际失败重新计时 |
| 心跳停滞时四轴字段仍有效 | ADS 还能读到冻结内存，机器状态已失效，但位置、速度和报警灯仍像实时反馈 | `MachineMonitorSnapshot.WithoutMachineAvailability` 同时使整帧四轴字段失效；保留心跳值供诊断 |
| 替换失联客户端时遗漏释放 | 显式再次调用连接可能遗留旧 ADS 客户端、端口和符号句柄 | `AxisService.ConnectAsync` 替换前释放原客户端，清除本地授权及历史快照；连接返回后复查取消 |
| 错误描述只取根异常 | 外层变量名、操作步骤、撤销失败提示可能丢失 | `AdsDiagnostics.DescribeException` 保留外层步骤与底层原因，聚合错误分别保留各分支 |

心跳有效性修复针对 `MachineMonitorService` 发布的监控快照。手动页面使用独立的 `AxisService.ReadSnapshotAsync`，它目前没有同样的心跳新鲜度校验，见下文限制。

## 仍需优先处理的代码问题

### 1. 手动客户端运行中断线、旧句柄失效后没有统一恢复流程

首次成功后的连接任务已结束。`AxisService.ReadSnapshotAsync` 遇到读取失败只记录错误，控制权维护循环遇到失败只使本地授权反馈无效，没有重新连接或重建句柄。监控客户端有独立的恢复流程，因此两者可能显示不同状态。

核对了仓库随附 `InduLink.Protocols.Ads.dll` 和 `InduLink.Runtime.dll` 的静态方法与调用关系：

- ADS DLL 的产品版本包含来源提交 `d7b82233361162d7f66e89b0c5004077330b4d1b`，与 `lib/README.md` 一致。
- 连接丢失会置位传输丢失状态，显式连接才清除；当前直接使用的客户端没有后台重连任务。
- `ReadAnyAsync` 的变量句柄会缓存；读取报错不会自动删除失效句柄并重取，关闭客户端才清理缓存。
- Runtime 内另一种托管设备有重连循环，但本项目没有使用该托管设备，不能据此认为当前客户端具备自动恢复。

下一步应为手动客户端设计明确的恢复状态：先使本地操作许可与旧反馈无效，处理正在进行的请求，重建连接及句柄，再从 PLC 获取新的反馈。写入超时结果可能不确定，不得自动重放运动命令。恢复策略与现有停止/控制权逻辑有关，本次没有增加运行期自动恢复。

### 2. 共享通信锁的请求超时长于 PLC 心跳阈值

`AxisService.Authority.cs` 每轮等待 250 ms，再获取 `_operationGate`，随后写站点心跳并读控制权反馈。手动读写、运行诊断及现有点位通讯也使用该锁。

当前 `AxisServiceOptions` 的默认操作超时和工作区 `App.config` 均为 5000 ms；仓库 PLC 的 `FB_ControlAuthority` 以 3 秒不变判断站点失联，现有 `FB_FourAxisTrajectory` 使用 1 秒运行心跳阈值。一个在锁内等待至超时的普通请求就可能跨过这些期限，“每 250 ms 执行循环”不保证心跳每 250 ms 送达。

这说明超时预算、请求耗时和心跳调度之间存在冲突，不证明现场已经因此停机。本次保持现有串行写入和 PLC 阈值；后续需测量最大请求耗时，明确心跳与读写的调度预算，不能仅延长 PLC 心跳超时来掩盖问题。

### 3. 手动反馈与控制权诊断仍有可改进处

- `AxisService.ReadSnapshotAsync` 只校验监控布局，没有校验心跳是否继续变化；PLC 内存可读但任务停滞时，手动页面仍可能取得历史轴状态。本次只修正独立监控快照的可用性，未改变手动操作许可策略。
- 控制权 `ReadManyAsync` 检查到任一字段质量异常时抛通用“PLC 控制权反馈读取失败”，没有将每项变量的错误原因加入提示。底层批量读接口会把部分异常转换成无效质量返回值，定位时还需要区分网络错误与符号/类型错误。

## 当前检查通过或未见明确缺陷的部分

- Router 先启动，客户端后连接；退出时先取消/释放客户端，Router 最后释放。独立 Router 启动失败不会回退连接其它本机 Router。
- PLC 目标统一来自 `AdsAmsNetId`，独立 Router 的远端路由复用该值；配置保存后下一次启动应用，两个客户端使用同次启动快照。
- C# 监控布局明确使用 `Pack=1`、BOOL 1 字节，四轴各 22 字节，总计 164 字节；布局版本不符会拒绝解释。
- 监控读取失败不会伪造为零值；普通缺符号与已缓存句柄失效按不同路径处理。
- 手动命令、控制权维护和点位通讯共用串行锁；控制权请求先写动作，再写序号。连接成功不等于取得控制权。
- 随附库对写入超时/取消有结果不确定异常，应用没有为失败运动命令增加自动重试。

配置页仍允许独立 Router 本机 Net ID 与 PLC 目标填写相同值，缺少冲突的提前提示；各站身份及 Net ID 唯一性仍需按部署配置核对。工作区 `App.config` 关闭独立 Router，因此其中旧 Router 参数不参与当前系统 Router 连接；源配置也不能替代实际运行目录配置的核对。

- 既有 `tests/verify_axis_monitoring.py`：91 项断言通过。
